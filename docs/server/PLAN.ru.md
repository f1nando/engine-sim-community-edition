# Серверный Engine Simulator: Ubuntu, без звука

**Отложено по следующему решению пользователя:** сначала распространяемая
нативная Windows-сборка через GitHub Releases, без серверного развёртывания.
План ниже сохранён как возможное дальнейшее направление.

## Согласованные условия

- Сервер — Ubuntu; одновременно ожидается максимум 2–3 человека.
- Физика остаётся на C++ из native/, не переписывается на JS и не заменяется
  демонстрационными показаниями. Клиентский JS/TS нужен только для интерфейса.
- Звука нет: не создавать аудиоустройства/синтезирующие потоки, не передавать
  аудио. WebRTC и звуковая часть не входят в серверный этап.
- Браузер показывает приборы, графики и кнопки; команды получает сервер,
  расчётные значения возвращаются клиенту с временными метками симуляции.
- По умолчанию у каждого пользователя своя независимая симуляция. Одна общая
  управляемая несколькими пользователями симуляция не предполагается.
- Нативная Windows-версия остаётся рабочей, со своим звуком и интерфейсом.
  Пользователь принял её как хорошую контрольную точку перед серверным этапом:
  [../native/ACCEPTED-VERSION.ru.md](../native/ACCEPTED-VERSION.ru.md).
  Изменения общего ядра не должны ломать обычную desktop-сборку.

Это новый целевой вариант, а не готовая возможность текущего exe. Ubuntu-сборка,
API, веб-интерфейс и развёртывание пока не реализованы и не проверены.
Развёртывание не выполнялось; никаких удалённых установок/изменений не производилось.

### Предварительный осмотр

Предварительный read-only осмотр выполнен. Окружение пригодно для начала
Linux-прототипа, но достаточность для трёх simulations realtime не подтверждена.
Приватные имена SSH-профилей и параметры конкретной машины не публикуются;
локальная копия первоначальной записи сохранена вне Git. Службы, пакеты и
настройки сервера не менялись, нагрузочные тесты не запускались.

## Архитектура первого варианта

```text
Браузер: приборы, выбор каналов, график, общий курсор, кнопки
                       |
                  HTTPS / WSS
                       |
Шлюз: вход, проверка команд, до 3 сессий, таймауты, каталог двигателей
                       |
            отдельный C++ worker на сессию
                       |
          двигатель + трансмиссия + машина + dyno
```

Отдельные процессы изолируют состояние движка и статический вывод компилятора
скриптов. Один worker не принимает команды другой сессии. Сетевой шлюз не
блокируется на физическом расчёте. Процессные лимиты и контейнеры не заменяют
проверку входных сообщений и авторизацию.

Имена новых исходных каталогов определить при реализации, вне игнорируемого
старого /web/. Прежний JS-порт не возобновлять и его артефакты не перезаписывать.

## 1. Консольное ядро без GUI и аудио — первый приоритет

- [ ] Добавить отдельную цель сборки для C++ worker. Не тянуть DirectX, Windows
      window/input/audio, SDL, Discord, видеозапись и графические assets.
- [ ] Разделить физические зависимости и delta-basic: сейчас библиотека
      engine-sim в native/CMakeLists.txt линкуется с delta-basic.
- [ ] Добавить явный режим без аудио с сохранением прежнего поведения desktop
      по умолчанию. Сейчас startFrame меняет число шагов по задержке синтезатора,
      simulateStep пишет в синтезатор, loadSimulation инициализирует его.
      Просто не запускать проигрывание недостаточно.
- [ ] Использовать фиксированный шаг физики и планировщик по монотонным часам
      без аудиокоррекции; сохранять дробный остаток времени, не терять шаги
      при округлении. Время симуляции считать по завершённым шагам.
- [ ] При перегрузке не скрывать отставание и не менять точность расчёта молча:
      показывать отношение времени симуляции к реальному, ограничить накопление
      долга/нагрузку. Частота физики — отдельная явная настройка.
- [ ] Сохранить загрузку проверенных engine scripts. Проверить переносимость
      Piranha, Boost, Flex/Bison и чтения ресурсов моделей на Ubuntu.
      Аудиоресурсы не должны приводить к запуску DSP/аудиовывода.
- [ ] Устранить Windows/MSVC-зависимые места в физическом/скриптовом контуре,
      не меняя физические формулы ради сборки.
- [ ] Поднять один двигатель из фиксированного каталога, включить зажигание
      и стартер, вывести реальные RPM, dyno-момент и мощность в консольный протокол.
- [ ] Проверить завершение, повторную загрузку и ограниченный расход памяти;
      сравнить расчётные показания с нативной версией на одинаковых условиях.

Приёмка: успешная сборка и запуск на Ubuntu без графического/звукового устройства,
воспроизводимые команды и настоящие показания. Windows-сборка и её тесты остаются
рабочими. До этого этапа не заявлять готовность Linux или realtime.

## 2. Протокол данных и управление

- [ ] Версионированные сообщения: session ID, последовательность, engine/run ID,
      время симуляции; отдельно монотонное серверное время/показатель отставания.
- [ ] Команды: выбор двигателя по ID каталога, ignition, starter press/release,
      throttle, clutch, gear up/down, dyno enable/hold/speed, pause/reset.
      Числовые диапазоны, типы, частота команд и размер сообщения ограничиваются.
- [ ] При потере соединения отпускать временно удерживаемые команды (особенно
      стартер/газ); приостанавливать/завершать сессию по таймауту, освобождать CPU.
- [ ] Телеметрия ориентировочно 50 отсчётов в секунду симуляции. В сеть отправлять
      ограниченные пакеты, например 10–20 раз в секунду, а не каждую физическую
      итерацию. Частоты выборки и доставки — разные величины.
- [ ] Единый независимый от GUI каталог каналов: ID, название, единицы, источник,
      доступность, способ выборки. Перенести физические формулы из привязок
      приборов так, чтобы worker не зависел от UiElement и Oscilloscope.
- [ ] N/A и пропуски передавать явно; нечисловые значения не превращать в ноль.
      Буферы и очереди ограничить; медленный браузер не останавливает worker.
- [ ] После смены двигателя/сброса начинать новый run ID и очищать историю всех
      каналов на клиенте, не смешивая показания разных запусков.

В headless нет desktop FPS, latency/input buffer синтезатора и звуковых настроек.
Их не выдавать за существующие серверные измерения. Вместо них отдельно назвать
частоту выдачи телеметрии, стоимость шага/нагрузку worker и задержку сети.
FPS отрисовки браузера — локальная характеристика клиента.

## 3. Первый веб-интерфейс

- [ ] Один двигатель, запуск/газ/остановка/dyno, реальные RPM/момент/мощность.
- [ ] Большая нижняя область графика, общая временная ось и цветные шкалы.
- [ ] Клик по доступному прибору добавляет/убирает его линию, не сбрасывая
      другие; общий курсор читает синхронные отсчёты и честные N/A.
- [ ] Дальше подключить остальные физические каналы, каталог двигателей,
      трансмиссию/сцепление и настройки опыта. Не генерировать фальшивые значения
      ради повторения всех desktop-индикаторов.
- [ ] Показать соединение, ошибки, паузу, отставание симуляции и сброс истории.
- [ ] Сохранение выбранных каналов и настроек интерфейса локально в браузере.

Первый прототип может работать без анимированной модели двигателя; основная
задача — управление и измерения. Если нужна анимация, её рисует браузер из
серверных данных, а не GPU/видеопоток на сервере.

## 4. До трёх независимых сессий

- [ ] Ввести предел в 3 активных workers; четвёртому клиенту понятный отказ/ожидание,
      а не неограниченный запуск процессов.
- [ ] Проверить изоляцию выбора двигателя, команд, истории и ошибок пользователей.
- [ ] Одновременно испытать 1, 2 и 3 двигателя, включая тяжёлые доступные модели;
      измерить CPU, RSS, отставание, задержку управления и доставку данных.
- [ ] Проверить перезапуск/отключение вкладки, потерю сети, зависание/падение worker,
      очистку после TTL и отсутствие бесконечного накопления очередей.

Число пользователей небольшое, но достаточность CPU без замеров не гарантировать.
Быстродействие одного ядра важно наряду с числом ядер. Для планирования нужны
версия Ubuntu, модель/количество CPU/vCPU и память фактического сервера.

## 5. Развёртывание

- [ ] Воспроизводимая Ubuntu-сборка/контейнер, фиксированные зависимости и
      лицензии источников, зависимостей, engine scripts и распространяемых assets.
- [ ] Непривилегированный пользователь; лимиты CPU/RAM/процессов на worker,
      таймауты компиляции/загрузки и whitelist двигателей.
- [ ] Не принимать произвольные engine scripts, пути файлов или shell-команды
      из браузера. Не публиковать worker/внутренний IPC напрямую в интернет.
- [ ] HTTPS/WSS через обратный прокси, закрытый доступ/авторизация для лаборатории,
      проверка Origin, ограничения соединений и размера/частоты команд.
- [ ] Health checks, ротация журналов, автоматический рестарт шлюза и очистка workers.
- [ ] Сначала проверить локально/staging, затем развёртывать на целевом сервере
      после согласования доступа. Не помещать пароли/ключи в репозиторий.

## Порядок

**Один консольный двигатель на Ubuntu → протокол → одна веб-сессия с графиком →
выбор физических показателей → три изолированные сессии → защищённое развёртывание.**

Каждый этап принимается по реальному запуску и тестам, а не по одному успешному
Windows build. Продолжать хранить состояние работ в этом плане.
